Documentation

OK2Ride is a W3C custom element, <ok2ride-check>, that runs a short cognitive capability check and reports whether the rider is alert and in control. It is meant to sit in the unlock flow of a micromobility app, but it has no opinion about your stack: it is one ES module, registers itself, renders inside a shadow root and talks to you through DOM events.

  • Randomised. Every run draws a set of tests from a pool of eight, so riders cannot rehearse one fixed task.
  • Precise. Reaction times are measured with performance.now() from the paint that reveals a stimulus.
  • Deterministic engine. A pure reducer drives the whole run; time and randomness are injected, so every transition is unit-tested and replayable.
  • Verifiable. The result carries a checksummed token bound to a nonce your server issued.
  • Self-contained. Zero runtime dependencies, about 19 KB gzipped, dark and light themes, keyboard accessible.

What it is not. A cognitive check estimates alertness and coordination; it is not a breathalyser and cannot measure blood alcohol. Treat a pass as one signal in your unlock policy, and treat the token as evidence to validate, not proof.

Getting started

1. Load the module

From a script tag:

<script type="module" src="/ok2ride.js"></script>

Or from npm inside a bundled app. Importing the package registers the ok2ride-check tag once and exports the engine types.

npm install ok2ride@{{PKG_VERSION}}
import 'ok2ride';
import type { AssessmentResult } from 'ok2ride';

2. Place the element

<ok2ride-check
  stage-count="2"
  difficulty="medium"
  time-limit-ms="90000"
  theme="dark"
  challenge-nonce="a-nonce-your-server-issued-for-this-unlock"
></ok2ride-check>

The element renders as a card up to 480 px wide that fills its container. Put it in a modal, a sheet or a page; it does not position itself.

3. React to the outcome

const el = document.querySelector('ok2ride-check');

el.addEventListener('capability-passed', async (e) => {
  const { verificationToken } = e.detail;
  const res = await fetch('/api/unlock', {
    method: 'POST',
    headers: { 'content-type': 'application/json' },
    body: JSON.stringify({ vehicleId, token: verificationToken }),
  });
  if (res.ok) showUnlocked();
});

el.addEventListener('capability-failed', (e) => {
  // e.detail.failureReason tells you why; e.detail.failedTest which test ended the run
  showCoolDown(e.detail);
});

The rider starts the run from the element's own Start check button. You can also call el.start() yourself, and el.reset() to abort and return to the idle screen.

Frameworks

Custom elements work in every framework. The only thing to remember is that the outcome arrives as DOM events, which some frameworks do not bind declaratively.

React

import { useEffect, useRef } from 'react';
import 'ok2ride';
import type { OK2Ride, AssessmentResult } from 'ok2ride';

export function RideCheck({ nonce, onPass }: { nonce: string; onPass: (r: AssessmentResult) => void }) {
  const ref = useRef<OK2Ride>(null);

  useEffect(() => {
    const el = ref.current;
    if (!el) return;
    const handler = (e: CustomEvent<AssessmentResult>) => onPass(e.detail);
    el.addEventListener('capability-passed', handler);
    return () => el.removeEventListener('capability-passed', handler);
  }, [onPass]);

  return <ok2ride-check ref={ref} stage-count="2" challenge-nonce={nonce} />;
}

Add the tag to JSX.IntrinsicElements if your TypeScript setup complains; React 19 types custom elements with plain attributes.

Vue

<ok2ride-check
  stage-count="2"
  :challenge-nonce="nonce"
  @capability-passed="onPass($event.detail)"
  @capability-failed="onFail($event.detail)"
/>

Tell the Vue compiler the tag is custom: compilerOptions.isCustomElement = (tag) => tag === 'ok2ride-check'.

Server-side rendering

The element class extends HTMLElement, so import the package from client code only, or behind a typeof window !== 'undefined' guard. The token helpers have a separate DOM-free entry, see Server verification.

The eight tests

Each test is a self-contained module with its own stages, scoring and screen. The pool, and the number drawn, are yours to configure.

Reaction (pvt)

A Psychomotor Vigilance Task in its brief form. After a random foreperiod of 1 500–4 500 ms the panel flashes yellow and the rider taps it. Three consecutive valid taps pass the test; any invalid trial resets the streak.

Reaction timeOutcomeEffect
tap before the flash, or < 100 ms afterFalse startTrial invalidated, streak reset, counted (fail after 3).
100–450 msValidStreak +1.
> 450 msLapseStreak reset, counted against max-lapses.
no tap within 2 000 msLapse (timed out)As above; excluded from mean RT.

These thresholds are fixed by protocol and do not change with difficulty.

Steering (spatial)

A steering dial shows a target arc at a random angle between 25° and 65° to either side. The rider rotates the handlebar into the arc by dragging around the pivot, or by tilting the phone when the rider opted in on the instruction screen, and releases. The window expiring while the handlebar sits inside the arc also passes. Keyboard: arrows steer, Shift for 5° steps, Enter locks in.

Go / Stop (go-no-go)

Six signals, each after a 0.7–1.6 s foreperiod, stay up for 900 ms. Green GO must be tapped; red STOP must be left alone. Two of the six are STOP, never the first. Taps on STOP and anticipations are commission errors; unanswered GO signals are omissions.

Number trail (trail)

Numbers are placed on distinct cells of a 4×4 grid with a little jitter. The rider taps them in ascending order. Wrong taps flash the board and count as errors; taps on numbers already collected are ignored.

Pattern memory (sequence)

On a 3×3 grid, tiles light up one after another (600 ms on, 250 ms off; never the same tile twice in a row). Once the pattern has played the rider repeats it. One wrong tile fails the test immediately.

Colour match (stroop)

Five rounds. A colour word (RED, GREEN, BLUE, YELLOW) appears written in an ink colour that differs from the word four times out of five. Four buttons with swatches offer the answer; the rider taps the ink colour. Each round times out after 3 s and counts as an error.

Time sense (timing)

Two rounds. A target interval of 2.5–4.5 s is named and then nothing on screen marks it passing — no countdown, no clock. The rider taps when they judge it has elapsed, and the signed error is scored against the tolerance. A round left untapped is abandoned 3 s past the target and counts as a miss. Interval judgements are not reaction times, so they are excluded from the run's RT aggregate.

Odd one out (search)

Three rounds. A field of identical letters on a 4×4 grid hides a single confusable different one (T among Ls, O among Qs, M among Ws, and so on, either way round). The rider taps the odd symbol; a wrong tap or a round that runs out after 6 s counts as an error. Each find contributes its reaction time to the run aggregate.

Run flow & timing

A run is a deterministic finite state machine. The framework stages are:

IDLE→ INSTRUCTION→ TEST_INTRO→ test stages…→ TEST_INTRO→ test stages…→ EVALUATED

Pressing Start check draws the plan and shows the instruction screen, which lists the drawn tests. Acknowledging it starts the overall clock and shows the intro for the first test; pressing Go enters that test's own stages. When a test passes, the next intro appears; when one fails, the run is evaluated immediately.

TestStage types
pvtPVT_AWAITING_STIMULUS → PVT_STIMULUS_ACTIVE → PVT_RESULT_DISPLAY, repeated per trial
spatialSPATIAL_MATCHING
go-no-goGNG_AWAITING → GNG_STIMULUS_ACTIVE → GNG_RESULT_DISPLAY, repeated per signal
trailTRAIL_ACTIVE
sequenceSEQUENCE_SHOWING (one step per tile, lit and unlit) → SEQUENCE_INPUT
stroopSTROOP_TRIAL → STROOP_RESULT_DISPLAY, repeated per round
timingTIMING_RUNNING → TIMING_RESULT_DISPLAY, repeated per round
searchSEARCH_ACTIVE → SEARCH_RESULT_DISPLAY, repeated per round

How reaction times are measured

  • Every tap handler samples performance.now() as its very first statement, before any other work, and passes that timestamp into the state machine.
  • Flash stimuli (reaction, Go/Stop) are revealed inside requestAnimationFrame: the onset timestamp is taken in that frame callback, immediately before the paint that shows the flash. RT is tapTime − onset.
  • The engine arms exactly one timer per stage, described by timerEffectFor(). Stale timers (for example a stimulus timeout that fires after the rider already tapped) are ignored because the reducer returns the same state for actions that no longer apply.
  • If the tab is hidden, animation frames pause, so a stimulus is never "shown" while nobody can see it. The overall time limit keeps running.
  • Pointer input uses pointerdown, not click, so there is no tap delay and no double firing. Keyboard uses Enter and Space.

Removing the element from the document during a run abandons the run silently and clears every timer; reattaching shows the idle screen.

Server verification

The result carries a verificationToken of the form ok2r1.<base64url claims>.<fnv1a-64 checksum>. The claims are:

ClaimMeaning
vToken version, 1.
sidSession id.
nonceYour challenge-nonce, or null.
okPassed.
iatIssued-at, ISO-8601.
ctCompletion time in ms.
rtMean reaction time in ms, or null.
lp, fsLapse and false-start counts.
seSteering error in degrees, or null.
plThe plan, comma-separated test ids.

The token is tamper-evident, not unforgeable. It is produced in the browser, so a hostile client can produce any token it likes. The checksum protects against corruption and casual tampering; the nonce protects against replay. Your backend must be the authority: issue a nonce per unlock attempt, accept each nonce once, and require freshness.

The token helpers ship in a DOM-free entry so they run in Node, Deno, Bun or an edge runtime:

import { decodeVerificationToken } from 'ok2ride/token';

export async function unlock(req) {
  const { vehicleId, token } = await req.json();
  const claims = decodeVerificationToken(token);          // null if malformed or checksum mismatch
  if (!claims || !claims.ok) return deny('failed');

  const challenge = await challenges.take(claims.nonce);  // one-time use: removes it
  if (!challenge || challenge.userId !== req.user.id) return deny('unknown-nonce');
  if (Date.now() - Date.parse(claims.iat) > 2 * 60_000) return deny('stale');
  if (Math.abs(Date.now() - challenge.issuedAt - claims.ct) > 10 * 60_000) return deny('implausible');

  await vehicles.unlock(vehicleId, { checkedAt: claims.iat, meanRt: claims.rt, plan: claims.pl });
  return ok();
}

Recommended policy on top of the token: rate-limit attempts per user, log the full AssessmentResult alongside the unlock for audit, and treat repeated failures as a cool-down rather than a hard block.

Theming

The element ships a dark theme tuned for night-time outdoor use and a light theme for daylight. Switch with the theme attribute; it applies instantly.

const prefersLight = matchMedia('(prefers-color-scheme: light)');
el.theme = prefersLight.matches ? 'light' : 'dark';
prefersLight.addEventListener('change', (e) => (el.theme = e.matches ? 'light' : 'dark'));

Accessibility

  • Every interactive surface is keyboard operable: Enter or Space taps panels and buttons, arrow keys steer the handlebar, Tab moves between tiles and numbers.
  • The tap panel and dial carry role="button" and role="slider" with live values; feedback lines are aria-live="assertive"; the stage label is aria-live="polite".
  • Colour is never the only carrier of meaning: GO/STOP and pass/fail are also spelled out, and the Stroop buttons are labelled by name.
  • Contrast targets outdoor readability: large type, thick borders, a saturated yellow stimulus with dark text.
  • prefers-reduced-motion disables the few transitions and the error shake.
  • Touch targets are at least 48 px; timed panels use touch-action: none so a tap never scrolls the page.

Timed tests are inherently hard for some riders. If your policy allows, expose an alternative verification path for users who cannot complete them, and use easy difficulty rather than removing tests.

Engine API

The state machine is exported for hosts that want to replay runs, build custom UIs or simulate policies. It is pure: time and randomness come in through an environment object.

import { createInitialState, reduce, resolveConfig, timerEffectFor, selectPlan } from 'ok2ride';

const config = resolveConfig({ difficulty: 'hard', stagePool: 'pvt,stroop', stageCount: 2 });
let state = createInitialState(config, 'session-1', 'nonce-1');

const env = (now) => ({ now, epochMs: Date.now(), random: Math.random });

state = reduce(state, { type: 'START_ASSESSMENT' }, env(0));           // draws state.plan
state = reduce(state, { type: 'ACKNOWLEDGE_INSTRUCTIONS' }, env(1000));
state = reduce(state, { type: 'BEGIN_TEST' }, env(1200));

const timer = timerEffectFor(state, 1200);
// e.g. { action: { type: 'TRIGGER_STIMULUS' }, delayMs: 2987 }

Example app: OK2Ride Bikes

The repository ships a complete integration in examples/bike-rental/: a small bike-rental web app with its own API server. It is the quickest way to see the widget inside a real unlock flow, and its server shows the verification rules from the previous sections as working code.

npm run rent    # http://localhost:5174
  1. The rider picks a bike on the map. City bikes need 2 tests; e-bikes and cargo bikes need 3.
  2. The app requests a challenge. The server returns a one-time nonce with the stage-count and difficulty for that bike type.
  3. The app mounts <ok2ride-check> with those attributes and calls start(), so the rider lands on the instructions.
  4. On capability-passed, the token goes to POST /api/rentals. The server checks the checksum, outcome, nonce owner, single use, expiry, bike, freshness, timing and test count, then returns an unlock code.
  5. On capability-failed, the token goes to POST /api/checks/failed, which consumes the nonce and starts a 30-second cooldown shown in the app.

The rules live in examples/bike-rental/server/store.ts, each with a unit test. The HTTP layer is a Connect-style middleware, so the same code runs under Vite, Express or a bare node:http server.

Adding a test

A test is two files and one id.

  1. Add the id to TestId and TEST_IDS in src/types.ts, plus its stage variants, result interface and failure reasons.
  2. Create src/tasks/<name>.ts exporting a TaskModule: stageTypes, start(config, env), reduce(stage, action, config, env) returning noop | stage | done, and timerEffect(stage, config, now). Register it in src/tasks/index.ts.
  3. Create src/components/screens/<name>.ts exporting a ScreenFactory that builds its nodes once and patches them on every state change. Map the stage types to it in src/components/screens/index.ts, and add a name and description to TEST_INFO.
  4. Write reducer tests with an injected random and a DOM test under happy-dom, following the existing ones.

The core never needs to change: plan selection, intros, time limits, evaluation and events all work from the module contract.

FAQ

Can riders cheat by automating taps?

The random draw, random foreperiods, random targets and the nonce make scripted replays impractical, but nothing running in a browser is tamper-proof. Combine the check with server-side nonces, rate limits and your existing fraud signals.

Why does a valid tap sometimes read a few milliseconds high?

Onset is sampled at the animation frame that reveals the stimulus; the actual pixels appear at the next display refresh, up to one frame later. This bias is constant and well under the 100 ms and 450 ms thresholds.

Tilt steering does not appear on my phone.

The toggle only shows when the steering test is in the plan and the browser exposes DeviceOrientationEvent. iOS additionally requires a secure context (HTTPS) and a permission prompt, which the toggle triggers.

Can I always include the reaction test?

Set stage-pool="pvt" with stage-count="1" for reaction only, or a pool of two with stage-count="2" to always run both. A "required test plus random extras" mode is a small change to selectPlan if you need it.

Does it work offline?

Yes. The element has no network dependency. Only your unlock call needs connectivity.
